# Обращение к результатам соседних задач

Дата: 2026-10-03. Статус: предложение для обсуждения, реализация не начата.
Ветка: `design/session-result-references`.

## Сценарий и допущение

Пользователь пишет агенту: «смотри на результат в 21». Агент читает результат
указанной задачи PromptPilot и использует его для текущей работы. Пока предполагаем,
что 21 — номер задачи, а не provider session_id или время. Это требует уточнения.
Чтение результата не продолжает чужую сессию и не отправляет в неё сообщения.

## Что уже существует

- `TaskInDB` хранит `result`, `error`, `verdict`, статус, время, рабочую директорию,
  `session_id`, `parent_task_id` и сведения о worktree.
- `GET /api/tasks/{task_id}` возвращает запись задачи с результатом.
- `pp status <id>` обрезает результат до первых 500 символов.
- `effective_prompt()` собирает задание и приписку человека перед запуском.
- Worker передаёт локальному процессу `PP_TASK_ID`.
- Workflow уже передаёт отчёт предыдущего исполнителя в новый запуск;
  общий механизм чтения произвольной задачи пока отсутствует.

## Варианты

1. **Команды чтения и инструкция агенту (рекомендуется).** Агент понимает явную
   ссылку в естественном языке и вызывает команду. Отчёты читаются по необходимости.
   Требуется доступный CLI и доступ к нужному экземпляру PromptPilot.
2. **Подстановка отчёта перед запуском.** Пользователь задаёт структурированную
   ссылку, например `#task:21`, worker прикладывает результат. Работает без инструментов
   у агента, но увеличивает начальный контекст и не покрывает новые ссылки в живом диалоге.
3. **MCP-инструменты чтения.** Удобны для клиентов с MCP, но требуют отдельного
   сервера и настройки каждого провайдера. Можно добавить поверх общего сервиса позже.

## Предлагаемый первый этап

Добавить сервис чтения, общий для CLI и API. Предлагаемые команды:

```text
pp context task 21 --json
pp context task 21 --offset 0 --limit 12000 --json
pp context recent --current-task 34 --limit 10 --json
```

Первая команда возвращает метаданные и ограниченный фрагмент сохранённого результата.
Ответ включает `task_id`, статус, время результата, `verdict`, рабочую директорию,
ветку/worktree, результат, ошибку и сведения о пагинации: `total_chars`, `offset`,
`next_offset`, `truncated`. Ограничение нельзя выдавать за полный отчёт.
Постраничное чтение должно возвращать идентификатор снимка; при изменении результата
между запросами клиент начинает чтение нового снимка, не склеивает разные версии.

`recent` возвращает только краткие карточки соседних задач того же проекта.
Для локальных задач проекта сопоставляется исходная директория репозитория, а не
временный путь worktree. Отдельно учитывается машина: одинаковый путь на разных
машинах не означает один проект. Список не включает полный текст соседних отчётов.
Явное обращение по ID может ссылаться на другой проект; в ответе это должно быть видно.

В промпт запуска добавить короткую инструкцию: ты выполняешь задачу №N; по явной
просьбе человека о результате задачи вызови команду чтения. Указать проверенный
способ запуска CLI и источник данных. Инструкция должна попадать и в headless,
и в herdr-запуски. Не разбирать свободный русский текст регулярными выражениями
в worker: естественную ссылку понимает сам агент. Одно число без контекста не
является ссылкой. Чтение соседних результатов не запускается автоматически.

Полученный отчёт — контекст с обозначенным источником. Он не меняет инструкции
текущей задачи. Выводы о состоянии кода агент проверяет по рабочему дереву;
результат из другой ветки сам по себе не означает наличие изменений здесь.

## Границы и ошибки

- Несуществующая/удалённая задача: явный ответ «задача не найдена».
- Pending/running без отчёта: «сохранённого результата пока нет», без автоматического
  ожидания. Если результат сохранился от прошлого запуска, обозначить это как
  предыдущий результат; не представлять его текущим прогрессом.
- Failed/cancelled: вернуть доступный отчёт и ошибку со статусом.
- Полный диалог провайдера и живой экран не входят в первый этап: сохранённый
  `result` не гарантирует наличие всей истории сессии.
- Локальный CLI должен читать ту же БД, что обслуживающий worker; отдельно
  установленный PromptPilot с другой БД не должен молча давать результат другого №21.
- SSH/herdr на другой машине требует доступа к исходному экземпляру через API
  либо доставки снимка отчёта. Локальный путь БД там недостаточен. Первый этап
  ограничить локальным выполнением; удалённому агенту явно сообщать о недоступности
  функции, пока транспорт не реализован.
- Новая функция чтения не должна выдавать агенту дополнительные операции записи
  или обходить существующую авторизацию API.

## Места будущих изменений и проверка

Выделить `promptpilot/task_context.py` для формирования ответа и снимков;
добавить команды в `cli.py`, при необходимости специализированные GET-маршруты
в `api.py`, инструкцию запуска в `worker.py` и соответствующую ветку herdr.
Изменение схемы tasks для первого этапа не требуется; необходимость хранения
снимков отдельно определить при утверждении дизайна.

Проверить чтение длинного отчёта без потери фрагментов, смену снимка между страницами,
отсутствующую задачу, running после retry со старым результатом, failed с ошибкой,
соседние задачи в worktree и выбор нужной БД. Отдельно проверить доставку инструкции
в локальный Codex/Claude и herdr. Интеграционные проверки делать на временной БД.

## Решение перед реализацией

Уточнить, что означает «21», и подтвердить первый этап: чтение сохранённого результата
по явной ссылке, плюс краткий список ближайших задач того же проекта. Затем оформить
окончательный дизайн и план реализации. Этот документ фиксирует исследование и
предложение, а не утверждённую спецификацию.
